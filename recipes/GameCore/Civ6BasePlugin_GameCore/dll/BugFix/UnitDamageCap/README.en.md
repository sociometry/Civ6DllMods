# UnitDamageCap

> English | [中文](README.md)

> Category: **BugFix** · Back to [Project Overview](../../../README.md)

Fixes "a unit whose hit points exceed 100 can no longer be killed by damage".

## The defect

XP2's `Unit::Instance::SetDamage` (RVA `0x3A5A60`) clamps damage to the **global constant**
`Context::Globals::ms_pkParameters->COMBAT_MAX_HIT_POINTS` (default 100):

```asm
13f3c5a87  44 8B 80 E8 01 00 00   mov r8d, [rax+1E8h]   ; COMBAT_MAX_HIT_POINTS
13f3c5a8e                        call Utilities::Range  ; Range(damage, 0, the value above)
```

The Base build (`0x18029CC40`) does one extra step at the same spot: it looks up the **`MaxHitPoints` property** from
`unit->m_kProperties(+0x1F0)` by hash `0x7D3FC711` and uses that as the cap, falling back to the global constant only
when the lookup fails. XP2 deleted that step.

**Consequence**: when a MOD raises a unit's `MaxHitPoints` above 100, `SetDamage` writes at most 100,
never reaches `MaxHitPoints`, and the unit stops dying.

`ChangeDamage(+n)` is only a thin shell around `SetDamage(m_iDamage + n)`, so changing the single place in
`SetDamage` covers every damage path.

## The fix: install a detour inside the function

We neither reimplement the whole function nor "call the original and then patch the value in" (that would write twice, fire the event twice and bypass the dirty flag).
The approach is to install a detour on **the single instruction that reads the cap**:

```asm
hook site  13F3C5A87  44 8B 80 E8 01 00 00   mov r8d, [rax+1E8h]   ; global cap
jump-back  13F3C5A8E                            call Utilities::Range
```

The detour (generated by asmjit, placed in the plugin DLL's `.uhook` section) calls `GetMaxDamage(unit)` to obtain the real cap,
writes it into `r8d` and then jumps back to `0x13F3C5A8E`. The replaced 7-byte instruction is moved into the trampoline by MinHook;
this module does not need to call it (we have already substituted our own value).

This yields:

- `SetDamage` **executes once and assigns once**;
- `UNIT_DAMAGE_CHANGED` fires once, and the value is the final value;
- `MoveAssignmentDo` runs as usual, and **FAutoVariable's dirty-flag mechanism is fully preserved** (multiplayer sync is unaffected);
- apart from the one replaced instruction, not a single byte of the function's logic — cancelling Heal and the like — is touched.

## The InstallHook target need not be the function entry

Global's `UnlockModelLimit` is used exactly this way — the hook site is in the middle of the `AddResource` function
(RVA `0x940F31`), and the end of the detour does `xchg+ret` back into the middle of it (`jumpBack = hookAddr + 0xE`).
This module follows the same pattern and is the first use of this route in the GameCore domain.

**Why use `InstallHook` instead of hand-writing a far jump**: MinHook uses an `FF 25` absolute jump internally and handles long distances itself.
This module once tried a hand-written `jmp rel32` patch, which proved unworkable in practice — the plugin DLL and GameCore are about 131000 GB apart,
far beyond rel32's ±2GB (`VirtualAlloc` returned an address 1528 GB from the patch site). Handing it to MinHook is the correct answer.

## Putting the detour in the `.uhook` section: W^X and a page of its own

```cpp
#pragma section(".uhook", read, write)
__declspec(allocate(".uhook")) alignas(4096) unsigned char g_detourCode[4096];
```

- **No leak**: the section lives inside the plugin DLL image and is reclaimed when the module unloads. The GameCore plugin is reloaded on every match entry and exit, so using `VirtualAlloc` would leak once per match;
- **W^X**: the section is declared read+write (not executable); after writing, `VirtualProtect(PAGE_EXECUTE_READ)` switches it to RX and `FlushInstructionCache` is called, leaving no permanent RWX page. **The order must not be reversed** — once `InstallHook` rewrites the entry, a game thread may jump in at any moment, and by then the code page must already be executable;
- **`alignas(4096)` gives it a page of its own**: `VirtualProtect` works per page. If several slots shared one page, switching the page back to RW when installing the second hook would make the first detour — which may be **executing** — non-executable and crash.

**Why the detour must live in the `.uhook` section**: the Loader validates detour address ownership with `GetModuleHandleExW(FROM_ADDRESS)`;
pages allocated by `VirtualAlloc` / `JitRuntime` belong to no module and are rejected
(`InstallHook rejected: caller/callback is not an active plugin`).

## Two asmjit pitfalls (measured)

### Pitfall one: `a.jmp(addr)` is not a direct jump

| Form | What is actually emitted | Note |
| --- | --- | --- |
| `a.jmp((uint64_t)addr)` | `FF 25 02 00 00 00` + inline pointer (16 bytes) | **Indirect jump** — it reads 8 bytes at the target and jumps through them as a pointer, so it is not "jump to that address"; using it always crashes |
| `a.jmp(x86::ptr(addr))` | `RelocOffsetOutOfRange` | Error; unusable |
| `a.jmp(x86::rax)` | `FF E0` | ✅ do `a.mov(x86::rax, addr)` first, then jump through the register — absolute address, no distance limit |

### Pitfall two: failed emits are silently dropped

For an invalid operand asmjit only records it in the emitter's local `err`, while `rt.add()` still returns `kErrorOk`, and that
instruction is silently dropped — so every emit must be checked explicitly (the `UC_EMIT` / `Emit` macros).

## Targets

| Target | RVA | Note |
| --- | --- | --- |
| `Unit::Instance::SetDamage` | `0x3A5A60` | patch site `+0x27`, jump-back site `+0x2E` |
| `Unit::Instance::GetMaxDamage` | `0x3A39A0` | exactly the block in XP2 that "reads the MaxHitPoints property, falling back to the global" |

Before patching, the original instruction bytes (`44 8B 80 E8 01 00 00`) are compared with `memcmp`; on mismatch the patch is skipped, so it can never land in the wrong place.

> `Shutdown` is an **empty implementation**: when leaving a match the plugin unloads as a whole and the module memory is reclaimed
> by the engine, so actively calling `VirtualFree` on the trampoline would be dangerous instead — the patch bytes still point at it.
> Per [Plugin Development Guide](../../../../../../docs/PLUGIN_GUIDE.md) §6.3, patches are by design "applied and not restored".

## Log

```
[UnitDamageCap] hooked SetDamage+0x27; Range upper bound now Unit::GetMaxDamage() (detour=NNN bytes, orig=0x...)
```

> `NNN` / `0x...` are the runtime values of the `%u` / `%p` format specifiers; these two placeholders never appear in real output.
